# پایگاه داده عملیاتی Bamero

## منبع حقیقت داده‌های فروشگاه

WooCommerce منبع حقیقت محصولات، دسته‌بندی‌ها، قیمت، موجودی، سبد و سفارش‌هاست. Bamero Core برای داده‌های اختصاصی خود جدول‌های جداگانه و دارای پیشوند نصب WordPress می‌سازد؛ از ساخت جداول موازی برای محصولات و سفارش‌ها خودداری می‌شود.

## مهاجرت اختصاصی نسخه ۱

فایل wp-content/plugins/bamero-core/database/schema.sql دو جدول InnoDB می‌سازد:

- جدول bamero_otp_challenges: هش شماره تلفن، purpose، هش HMAC کد، انقضا، شمارنده تلاش، زمان مصرف، هش IP و شناسه پیامک.
- جدول bamero_rate_limits: bucket یکتا برای محدودسازی نرخ با شمارنده و زمان شروع پنجره.

مهاجرت هنگام فعال‌سازی/بارگذاری Bamero Core بر اساس bamero_db_version اجرا می‌شود. اجرای مجدد DDL امن و idempotent است. کد خام OTP در دیتابیس ذخیره نمی‌شود.

## آزمون دیتابیس واقعی

GitLab CI سرویس واقعی MariaDB 11.8.9 را راه‌اندازی می‌کند، migration تولیدی را روی آن اجرا می‌کند، اجرای دوباره را می‌آزماید و Engine و ایندکس‌ها را کنترل می‌کند. این تست از Mock یا SQLite استفاده نمی‌کند.

## پشتیبان‌گیری

اسکریپت ops/backup-database.sh از MariaDB در حال اجرا با mariadb-dump --single-transaction نسخه فشرده می‌گیرد، gzip را اعتبارسنجی و فایل‌های قدیمی‌تر از دوره نگه‌داری را حذف می‌کند:

    chmod 700 ops/backup-database.sh
    RETENTION_DAYS=14 BACKUP_DIR=/secure/offsite-staging ./ops/backup-database.sh

دایرکتوری مقصد باید روی فضای امن خارج از میزبان اصلی یا به‌صورت مقصد انتقال رمزگذاری‌شده mount شود. اجرای محلی به‌تنهایی پشتیبان خارج از سرور ایجاد نمی‌کند.

## الزامات پیش از production

- پیش از هر ارتقای MariaDB از volume فعلی backup قابل‌بازیابی تهیه و migration رسمی انجام شود؛ volume موجود حذف نشود.
- backup باید به مقصد خارج از میزبان منتقل و بازیابی دوره‌ای آن آزمایش شود.
- دسترسی DB فقط از شبکه داخلی اپلیکیشن مجاز باشد؛ پورت دیتابیس عمومی نشود.
- TLS بین میزبان‌ها، رمزهای قوی مجزا، least privilege و پایش فضای دیسک الزامی است.
- مهاجرت‌های بعدی باید نسخه‌دار، backward-compatible و دارای تست integration روی MariaDB هدف باشند.
