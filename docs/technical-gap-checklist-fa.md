# چک‌لیست شکاف‌های فنی و آمادگی بامرو

این سند فهرست تصمیم‌گیری است، نه اعلام آمادگی انتشار. هر مورد یک چک‌باکس قابل انتخاب دارد. «شاهد مشاهده‌شده» فقط به شواهد بررسی‌شده اشاره می‌کند؛ «فرضیه/پیشنهاد» نتیجه‌گیری اثبات‌نشده یا معیار پیشنهادی را جدا می‌کند. وضعیت‌ها: **موجود** یعنی نشانه یا پیاده‌سازی در مخزن هست؛ **ناقص** یعنی بخشی موجود است اما کافی نیست؛ **موک** یعنی نمونه/شبیه‌ساز صرفاً برای تست یا جایگزین موقت؛ **آزموده‌نشده** یعنی اجرای واقعی اثبات نشده است. اولویت P0 مانع ایمنی/انتشار است، P1 مانع پذیرش قابل اتکا، P2 بهبود پس از رفع موارد بالاتر.

## (A) اصلاحات واقعی مخزن/کد

### 1. [ ] P0 — بی‌اثرکردن تنظیمات توسعه‌ای ناامن در مسیر استقرار [موجود]
- **شاهد مشاهده‌شده:** `.env.example` رمزهای قابل‌حدسِ مخصوص توسعه و `WORDPRESS_DEBUG=1` دارد؛ Compose به‌صراحت برای استفاده محلی است و WordPress را فقط روی `127.0.0.1` منتشر می‌کند. این ترکیب به‌تنهایی نقص استقرار نیست، اما خطای رایج و خطرناک، کپی‌کردن همین مقادیر به محیط عمومی است. [1]
- **اقدام دقیق:** فایل نمونه را صریحاً فقط‌محلی نگه دارید؛ در راهنمای استقرار چک اجباری برای رد رمزهای نمونه و خاموش‌کردن debug در محیط غیرمحلی تعریف کنید. مطمئن شوید `.env` واقعی وارد Git نشده و هر رمز تکرارشده‌ای عوض شده است.
- **اثبات پذیرش:** آزمون/بازبینی استقرار با مقادیر نمونه باید fail شود؛ جست‌وجوی تاریخچه و تنظیمات CI برای اسرار انجام و نتیجه ثبت شود؛ `WORDPRESS_DEBUG` در پیکربندی staging/production خاموش باشد.

### 2. [ ] P1 — افزودن گیت‌های خودکارِ اسرار و پیکربندی [ناقص]
- **شاهد مشاهده‌شده:** `.gitignore` فایل `.env` و `wp-config.php` را کنار می‌گذارد و `.env.example` را مجاز می‌کند؛ اما شواهدی از secret scanning یا چرخش اسرار ارائه نشده است. [2]
- **اقدام دقیق:** secret scanning را برای commit و CI فعال کنید، فایل‌های حساس را از artifactها حذف کنید و روند چرخش اعتبارنامه را مستند کنید. این مورد جایگزین بررسی تاریخچه نیست.
- **اثبات پذیرش:** CI روی یک secret آزمایشی ساختگی fail کند؛ اسکن تاریخچه/شاخه‌ها گزارش پاک یا موارد رفع‌شده داشته باشد؛ هیچ کلید واقعی در مخزن یا log نباشد.

### 3. [ ] P1 — ثبت ماتریس نسخه و به‌روزرسانی وابستگی‌ها [ناقص]
- **شاهد مشاهده‌شده:** تگ‌های MariaDB و WordPress در Compose پین شده‌اند؛ این تکرارپذیری را بهتر می‌کند، اما تازگی وصله‌ها یا سیاست ارتقا را اثبات نمی‌کند. [3]
- **اقدام دقیق:** نسخه‌های پشتیبانی‌شده WordPress، WooCommerce، PHP، پایگاه‌داده، افزونه‌ها و imageها را با مالک، زمان بازبینی و روش rollback ثبت کنید؛ تغییر تگ‌ها پس از آزمون staging انجام شود.
- **اثبات پذیرش:** فهرست نسخه‌های واقعی staging و تاریخ آخرین بررسی امنیتی موجود باشد؛ ارتقای آزمایشی و rollback موفق ثبت شود.

### 4. [ ] P1 — حفظ ادغام WooCommerce مبتنی بر hook و پوشش رگرسیون [موجود]
- **شاهد مشاهده‌شده:** تم از پشتیبانی و hookهای WooCommerce استفاده می‌کند و template override ووکامرس مشاهده نشده است؛ این رویکرد بار نگهداری ارتقا را کم می‌کند. وجود hook یا تست ایستا، سازگاری زمان اجرا را ثابت نمی‌کند. [4]
- **اقدام دقیق:** الگوی hook-based را حفظ کنید و پس از نصب نسخه‌های واقعی WordPress/WooCommerce، تست ادغام برای wrapperها، breadcrumb، سبد و صفحه محصول اضافه کنید؛ فقط در صورت نیاز اثبات‌شده به override بروید.
- **اثبات پذیرش:** تست staging با نسخه‌های ثبت‌شده markup معتبر و بدون هشدار ناسازگاری نشان دهد؛ آزمون ارتقای WooCommerce نیز پاس شود.

### 5. [x] P1 — حفظ انتخاب ستون‌های محصول در تنظیمات WooCommerce [کد اصلاح شد؛ runtime هنوز آزموده‌نشده]
- **شاهد مشاهده‌شده:** مستندات WooCommerce می‌گوید `product_grid` محدودهٔ ستون‌های قابل انتخاب فروشگاه را تعیین می‌کند و قالب loop تعداد را در کلاس `columns-N` می‌گذارد. CSS قبلی کلاس‌های انتخاب‌شده را در دسکتاپ نادیده می‌گرفت. [5]
- **اقدام انجام‌شده:** CSS اکنون `columns-1` تا `columns-4` را در اندازهٔ عادی رعایت می‌کند؛ از عرض ۹۰۰ پیکسل به پایین، طرح واکنش‌گرا برای حالت‌های چندستونه به دو ستون می‌رسد، اما انتخاب تک‌ستونه را حفظ می‌کند. تست رگرسیون وجود قواعد را کنترل می‌کند.
- **اثبات باقی‌مانده:** تست منبع محلی باید پاس شود؛ سپس در staging چند مقدار واقعی تنظیم ستون و عرض‌های هدف را رندر کنید. قبولی تست متنی CSS به‌تنهایی اثبات رندر WooCommerce نیست.

### 6. [ ] P2 — بازبینی برند، متن ثابت و تصویر قهرمان [ناقص]
- **شاهد مشاهده‌شده:** تصویر قهرمان از اشکال CSS ساخته شده و نشان عمومی fallback است؛ متن فارسی برندمحور در کد ثابت است. این موارد کاتالوگ جعلی نیستند، ولی جایگزین دارایی/محتوای تأییدشده فروشگاه هم نیستند. [6]
- **اقدام دقیق:** مالک برند متن، لوگو و تصویر را تأیید کند؛ دارایی‌های مجاز را جایگزین یا صریحاً همین طرح CSS را انتخاب کند. پیام‌های حالت خالی/راه‌اندازی را به‌عنوان حالت عمدی حفظ کنید.
- **اثبات پذیرش:** تأیید محتوایی مالک و نمایش درست لوگوی سفارشی/جایگزین در قالب‌های اصلی ثبت شود.

## (B) دارایی‌های موک/نمونه/موقت برای جایگزینی یا برچسب‌گذاری

### 7. [ ] P1 — جداکردن FakeElement از ادعای تست مرورگر [موک]
- **شاهد مشاهده‌شده:** `FakeElement` فقط زیرساخت تست Node برای بخش کوچکی از DOM در تست ناوبری است؛ تست مرورگر، WordPress، WooCommerce یا checkout واقعی نیست. اشتباه رایج، برابر دانستن تست واحد با اثبات رفتار دسترس‌پذیری واقعی است. [7]
- **اقدام دقیق:** در توضیح تست و گزارش‌ها محدودیت harness را آشکار نگه دارید؛ آن را با تست مرورگر واقعی تکمیل کنید، نه اینکه خروجی آن را گواه conformance بنامید.
- **اثبات پذیرش:** گزارش CI صریحاً محدوده تست را مشخص کند و آزمون مرورگر staging جداگانه پیوند/گزارش داشته باشد.

### 8. [ ] P1 — تأمین کاتالوگ واقعی و تأییدشده در staging [آزموده‌نشده]
- **شاهد مشاهده‌شده:** کاتالوگ از داده‌های WooCommerce خوانده می‌شود و حالت بدون محصول/بدون WooCommerce پیام خالی یا راه‌اندازی نشان می‌دهد؛ کاتالوگ نمونه مشتری‌نما مشاهده نشده است. داده واقعی و تصاویر تأییدشده هنوز در محیط اجرایی اثبات نشده‌اند. [8]
- **اقدام دقیق:** مالک، محصولات، دسته‌بندی‌ها، قیمت، موجودی، تصاویر، متن جایگزین و وضعیت انتشار را تأیید و در staging بارگذاری کند؛ داده آزمایشی را از داده قابل انتشار علامت‌گذاری و جدا کند.
- **اثبات پذیرش:** صفحات دسته و محصول فقط داده مصوب را نشان دهند؛ وضعیت خالی و وضعیت نبود افزونه هم قابل فهم و بدون محصول ساختگی باشد.

### 9. [ ] P1 — تصمیم و آزمون درگاه Zibal، بدون فرض نصب/سازگاری [آزموده‌نشده]
- **شاهد مشاهده‌شده:** کد یا پیکربندی Zibal در مخزن مشاهده نشده؛ هیچ runtime، افزونه، دامنه یا اعتبارنامه‌ای ارائه نشده است. افزونه فهرست‌شده فقط نامزد بررسی است، نه انتخاب یا تأیید سازگاری. [9]
- **اقدام دقیق:** مالک پرداخت باید افزونه/نسخه و حساب پذیرنده را انتخاب کند؛ فقط در sandbox و با HTTPS، درخواست، callback و سپس verify سمت سرور آزموده شود. تطبیق مبلغ/شناسه سفارش، رویداد تکراری، لغو و خطا را بررسی کنید؛ موفقیت callback به‌تنهایی پرداخت موفق نیست.
- **اثبات پذیرش:** گزارش تراکنش sandbox نشان دهد verify سمت سرور موفق و تکرار callback idempotent است؛ سفارش ناموفق/لغوشده پرداخت‌شده نشود. تأیید پذیرنده برای محیط واقعی جداگانه ثبت شود.

### 10. [ ] P1 — تعیین تکلیف OTP پیامکی و سطح افزونه [آزموده‌نشده]
- **شاهد مشاهده‌شده:** پیاده‌سازی یا پیکربندی OTP در مخزن دیده نشده است. مستندات API پیامک، به‌تنهایی وجود ورود OTP آماده برای WooCommerce را اثبات نمی‌کند؛ برخی قابلیت‌های افزونه نیز به سطح اشتراک وابسته‌اند. [10]
- **اقدام دقیق:** مالک تصمیم بگیرد OTP الزام است یا خیر؛ اگر بله، افزونه/پلن، سرویس‌دهنده، بازیابی حساب، محدودسازی سوءاستفاده و ارسال پیام را در staging ارزیابی کند. در غیر این صورت، OTP را قابلیت موجود معرفی نکند.
- **اثبات پذیرش:** آزمون ثبت‌نام/ورود/بازیابی، محدودسازی ارسال و خطاها با حساب و پلن واقعی موفق باشد؛ هزینه و مالک پیکربندی ثبت شود.

### 11. [ ] P1 — جایگزینی دارایی‌های نمایشی با محتوای مجاز [ناقص]
- **شاهد مشاهده‌شده:** fallback لوگو و تصویرسازی CSS وجود دارد؛ هیچ شاهدی از تصویر محصول ساختگی مشتری‌نما نیست. این دو نباید با عکس محصول یا نشان تأییدشده اشتباه گرفته شوند. [6]
- **اقدام دقیق:** دارایی نهایی را از مالک دریافت کنید یا fallback را به‌وضوح حفظ کنید؛ برای تصاویر واقعی محصول، ابعاد، مجوز و متن جایگزین را همراه محتوا ثبت کنید.
- **اثبات پذیرش:** بررسی بصری صفحات اصلی و محصول هیچ دارایی ناخواسته/بی‌مجوز نشان ندهد؛ تصاویر محصول alt مناسب داشته باشند.

## (C) واقعیت‌های زنده/زمان اجرا که staging یا مالک لازم دارند

### 12. [ ] P0 — ایجاد staging واقعی WordPress و WooCommerce [آزموده‌نشده]
- **شاهد مشاهده‌شده:** هیچ runtime وردپرس/ووکامرس، افزونه نصب‌شده یا پیکربندی ارائه نشده؛ README نیز Compose را محلی می‌داند. قابلیت‌های کاتالوگ، سبد، حساب و سفارش به WooCommerce وابسته‌اند و از بررسی کد به‌تنهایی ثابت نمی‌شوند. [11]
- **اقدام دقیق:** مالک محیطی ایزوله با نسخه‌های پشتیبانی‌شده، TLS، داده آزمون و فهرست افزونه‌های مجاز فراهم کند؛ نسخه و تنظیمات را ثبت کنید.
- **اثبات پذیرش:** ورود به staging، نسخه‌ها، افزونه‌ها، صفحات اختصاص‌یافته فروشگاه/سبد/پرداخت/حساب و گزارش سلامت ثبت شوند.

### 13. [ ] P0 — آزمون کامل مسیر خرید و چرخه سفارش [آزموده‌نشده]
- **شاهد مشاهده‌شده:** cart/checkout/account/order، مهمان، موجودی، refund و وضعیت سفارش در runtime آزموده نشده‌اند. هیچ اتصال پرداختی تأیید نشده است. [12]
- **اقدام دقیق:** در staging مسیر مرور محصول، جست‌وجو، افزودن/تغییر سبد، خرید مهمان و حساب‌دار، پرداخت موفق/ناموفق/لغو، callback تکراری، کاهش موجودی و بازپرداخت را اجرا کنید.
- **اثبات پذیرش:** سفارش‌های آزمون با حالت و مبلغ درست ثبت شوند؛ موجودی فقط طبق رویداد معتبر تغییر کند؛ سفارش لغوشده/ناموفق موفق نشود؛ refund واقعی یا مسیر پشتیبانی آن مستند باشد.

### 14. [ ] P1 — اثبات امنیت استقرار عمومی، TLS و دسترسی مدیر [آزموده‌نشده]
- **شاهد مشاهده‌شده:** Compose محلی TLS، reverse proxy یا سخت‌سازی تولید ندارد؛ این محدوده اعلام‌شده است، نه پیکربندی production. MFA، حساب کم‌دسترسی و محدودسازی ورود نیز اثبات نشده‌اند. [13]
- **اقدام دقیق:** مالک زیرساخت TLS معتبر، تنظیم درست proxy و forwarded headers، محدودکردن دسترسی origin/مدیر، MFA، حداقل دسترسی، غیرفعال‌کردن ویرایش فایل از داشبورد و rate limit را پیکربندی کند.
- **اثبات پذیرش:** اسکن/بازبینی پیکربندی staging، هدرها و دسترسی‌ها موفق باشد؛ ورود بدون MFA برای حساب‌های مدیر مجاز نباشد؛ backend/DB از بیرون قابل دسترسی مستقیم نباشد.

### 15. [ ] P1 — آزمون RTL، بازچینی، صفحه‌کلید و فناوری کمکی [آزموده‌نشده]
- **شاهد مشاهده‌شده:** کد نشانه‌های مثبت مانند ویژگی‌های منطقی RTL، breakpoint، skip link، focus style و کنترل منو دارد؛ تست FakeElement و بررسی منبع، رندر مرورگر یا انطباق WCAG را اثبات نمی‌کند. [14]
- **اقدام دقیق:** staging را در عرض‌های 320، 375/390، 768، 1024 و دسکتاپ، بزرگ‌نمایی 200٪/400٪، RTL/LTR و مرورگرهای هدف بررسی کنید؛ مسیر صفحه‌کلید و جفت‌های AT/مرورگر را اجرا کنید. کنتراست متن و حالت‌های کنترل را روی پس‌زمینه رندرشده اندازه بگیرید.
- **اثبات پذیرش:** گزارش viewport/browser/AT شامل مسیر فوکوس، بازگشت فوکوس، اعلان منو، خطا/موفقیت فرم و معیارهای کنتراست WCAG 2.2 AA باشد؛ مشکل بحرانی باز نماند.

### 16. [ ] P1 — راستی‌آزمایی SEO و پاسخ HTTP زنده [آزموده‌نشده]
- **شاهد مشاهده‌شده:** تم title-tag و `wp_head` دارد و قالب 404 دارد؛ این‌ها وجود metadata نهایی یا HTTP 404 واقعی را ثابت نمی‌کنند. افزونه، تنظیمات وردپرس و هاست ممکن است خروجی را تغییر دهند. [15]
- **اقدام دقیق:** با دامنه staging مجاز، HTML و header/status صفحه خانه، محصول، آرشیو، جست‌وجو، صفحه‌بندی و URL ناموجود را بررسی کنید؛ عنوان، description، canonical، OG، favicon، schema، noindex، robots و sitemap را از خروجی واقعی استخراج کنید.
- **اثبات پذیرش:** URL ناموجود status واقعی 404 بدهد؛ sitemap/robots قابل دریافت و سازگار با تنظیمات باشند؛ canonical و metadata تکراری/غلط نباشند؛ هر schema با محتوای قابل مشاهده و سیاست‌های موتور جست‌وجو منطبق باشد. هیچ ادعای رتبه یا index شدن از این آزمون نتیجه نمی‌شود.

### 17. [ ] P1 — پشتیبان‌گیری، بازیابی و لاگ امن [آزموده‌نشده]
- **شاهد مشاهده‌شده:** در Compose محلی volume وجود دارد، اما مدرک پشتیبان رمزگذاری‌شده خارج از میزبان، نگهداری نسخه یا تمرین restore موجود نیست. [16]
- **اقدام دقیق:** مالک عملیات پشتیبان دیتابیس و uploads، دسترسی محدود، retention، رمزگذاری و پایش/چرخش لاگ را تعیین کند؛ اسرار و داده پرداخت حساس وارد log نشوند.
- **اثبات پذیرش:** بازیابی زمان‌دار در محیط ایزوله از نسخه پشتیبان انجام و سلامت سفارش/فایل‌ها بررسی شود؛ گزارش restore و سیاست نگهداری موجود باشد.

### 18. [ ] P1 — آزمون وب‌هوک، امضای درخواست و idempotency [آزموده‌نشده]
- **شاهد مشاهده‌شده:** رفتار callback درگاه و تنظیم webhook زمان اجرا بررسی نشده و وجود پیاده‌سازی/پیکربندی امضای امن در دسترس نیست. [17]
- **اقدام دقیق:** برای هر endpoint واقعی، اعتبارسنجی امضا/secret، جلوگیری از replay، idempotency، مدیریت retry و ثبت خطا را با مالک افزونه/پرداخت تأیید کنید.
- **اثبات پذیرش:** درخواست با امضای غلط رد شود؛ رخداد تکراری اثر مالی/سفارش دوباره نسازد؛ retry و هشدار شکست در staging ثبت شود.

### 19. [ ] P1 — اندازه‌گیری ظرفیت و کارایی، نه استنتاج از ۱۰۰۰ MAU [آزموده‌نشده]
- **شاهد مشاهده‌شده:** هیچ داده سرعت، CWV، بار، افزونه، CDN، دیتابیس یا ترافیک واقعی ارائه نشده است. ۱۰۰۰ کاربر فعال ماهانه معادل هم‌زمانی، درخواست بر ثانیه یا ظرفیت checkout نیست. معیارهای عددی زیر **پیشنهادی** هستند، نه نتیجه مشاهده‌شده و نه تضمین رسمی WooCommerce. [18]
- **اقدام دقیق:** ابتدا پیش‌بینی اوج، مدت نشست و سهم عملیات پویا را از مالک بگیرید؛ سپس در staging هم‌ارز production بار مرور ناشناس، جست‌وجو، حساب، سبد و checkout را بسنجید. معیار پیشنهادی پروژه: ۳۰ دقیقه اوج پیش‌بینی‌شده و ۱۵ دقیقه ۲× اوج؛ خطای HTTP کمتر از ۱٪، p95 زمان پاسخ پویا ≤۸۰۰ms و پاسخ checkout ≤۲s به‌جز تأخیر درگاه؛ بدون اتمام منابع. CWV پیشنهادی در صدک ۷۵: LCP ≤۲٫۵s، INP ≤۲۰۰ms، CLS ≤۰٫۱.
- **اثبات پذیرش:** گزارش بار با هم‌زمانی/throughput، p95، خطا، CPU/RAM، workerهای PHP، اتصال و slow query دیتابیس، cache hit و جداسازی سبدها ارائه شود؛ RUM/CWV جداگانه برای موبایل/دسکتاپ ثبت شود.

### 20. [ ] P1 — تعیین تکلیف انتشار تغییرات Git و CI [آزموده‌نشده]
- **شاهد مشاهده‌شده:** شاخه ۲ commit جلوتر از `main` گزارش شده؛ push/merge به علت token نامعتبر GitHub و پاسخ API 403 suspension مسدود است. README تغییرکرده و گزارش audit محلی untracked گزارش شده‌اند. وضعیت فعلی remote/PR مستقل تأیید نشده است. [19]
- **اقدام دقیق:** مالک دسترسی GitHub، token معتبر و مجاز را از مسیر امن فراهم کند؛ تغییرهای intended را بازبینی، commit و سپس push/PR و CI را اجرا کند. اسرار را داخل گفتگو یا Git نگذارید.
- **اثبات پذیرش:** remote شاخه و PR به‌روز، CI سبز، diff و فایل‌های موردنظر بازبینی‌شده، و merge با تأیید صاحب مخزن ثبت شود.

## (D) بهبودهای اختیاری

### 21. [ ] P2 — سنجش سازگاری واقعی گالری و افزونه‌ها [آزموده‌نشده]
- **شاهد مشاهده‌شده:** CSS برای گالری/WooCommerce وجود دارد؛ تعامل گالری، کنترل‌های لمسی/صفحه‌کلید و تداخل افزونه‌ها در مرورگر اثبات نشده است. [14]
- **اقدام دقیق:** پس از تثبیت فهرست افزونه‌ها، گالری، گزینه‌های محصول، تعداد، فرم‌ها، خطاها، اعلان وضعیت و کنترل‌های لمسی را با کیبورد و AT آزمایش کنید.
- **اثبات پذیرش:** گزارش تست هر ترکیب مرورگر/افزونه، متن جایگزین تصاویر و مسیرهای خطا/موفقیت را پوشش دهد؛ کنترل drag-only بدون جایگزین نباشد.

### 22. [ ] P2 — بهینه‌سازی تصاویر و cache فقط بر اساس اندازه‌گیری [آزموده‌نشده]
- **شاهد مشاهده‌شده:** فونت محلی و قواعد محدودکردن عرض تصویر در CSS دیده می‌شود؛ حجم واقعی عکس‌ها، cache/CDN و هزینه افزونه‌ها معلوم نیست. [18]
- **اقدام دقیق:** پس از baseline، تصویر responsive و فشرده، cache دارایی ایستا و در صورت نیاز object cache/CDN را با آزمون جداسازی Cart/Checkout/My Account ارزیابی کنید؛ cache مشترک نباید نشست یا سبد کاربران را نشت دهد.
- **اثبات پذیرش:** مقایسه قبل/بعد شامل بایت تصویر، هدر cache، CWV و آزمون دو سبد مستقل باشد؛ بهبود بدون عارضه تأیید شود.

### 23. [ ] P2 — ارزیابی metadata/schema اختیاری با داده مصوب [ناقص]
- **شاهد مشاهده‌شده:** پیاده‌سازی صریح theme-owned برای OG، description، canonical، Product/LocalBusiness JSON-LD یا llms.txt در بررسی کد مشاهده نشده؛ خروجی افزونه/هسته و نیاز کسب‌وکار نامعلوم است. llms.txt را الزام Google تلقی نکنید. [20]
- **اقدام دقیق:** پس از بررسی خروجی runtime، تنها خلأ اثبات‌شده را رفع کنید؛ LocalBusiness فقط با تأیید هویت/نشانی واقعی مالک و Product فقط با داده واقعی محصول تولید شود.
- **اثبات پذیرش:** خروجی معتبر، بدون داده ساختگی و بدون تکرار schema/metadata در صفحات نمونه باشد؛ اعتبارسنجی ساختاری و سازگاری محتوا ثبت شود.

## ترتیب پیشنهادی فازها برای انتخاب کاربر

1. **فاز صفر — حفاظت و دسترسی:** موارد 1، 2 و 20؛ تأیید مرز local-only، پاکیزگی اسرار و رفع مانع Git/CI.
2. **فاز یک — staging و مالکیت:** موارد 12، 8، 9 و 10؛ انتخاب مالک محیط، داده، درگاه و تصمیم OTP، بدون فرض نصب یا سازگاری.
3. **فاز دو — پذیرش مسیرهای اصلی:** موارد 13، 14، 17 و 18؛ تجارت، امنیت، بازیابی و callback/webhook.
4. **فاز سه — تجربه و کشف‌پذیری:** موارد 15، 16، 4، 5 و 21؛ رندر واقعی، دسترس‌پذیری، SEO و یکپارچگی افزونه.
5. **فاز چهار — اندازه‌گیری و پالایش:** موارد 3، 19 و 22؛ چرخه وصله، ظرفیت و بهینه‌سازی مبتنی بر داده.
6. **فاز پنج — تصمیم‌های اختیاری:** موارد 6، 11 و 23؛ برند/دارایی و metadata پس از تأیید مالک.

این ترتیب **پیشنهاد برای انتخاب** است و هیچ موردی در این کار پیاده‌سازی نشده است. وضعیت گزارش‌شده: شاخه ۲ commit جلوتر از main؛ بررسی محلی Node و syntax در PHP 8.3.6 پاس شده؛ push/merge راه دور به‌علت GitHub token نامعتبر و API 403 suspension مسدود است؛ WordPress runtime و پیکربندی افزونه/ارائه‌دهنده وجود ندارد. این گزارش **Go Live** نیست و از تست ایستا آمادگی انتشار نتیجه نمی‌گیرد.
